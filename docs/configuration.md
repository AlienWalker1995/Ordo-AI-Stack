# Configuration Quick Reference

> Configuration is **rendered, not hand-edited**: the declarative source `ordo.yaml` (template `ordo.example.yaml`) is regenerated by the render engine into `out/.env`, `out/docker-compose.yml`, `out/manifest.json`, etc. Values that must survive a re-render go in the source: `site:` for env values the manifests interpolate, and the `overrides:` block for llama.cpp tuning only (`overrides.inference-engine-gpu.<key>` and `overrides.inference-engine-cpu.threads`; any other key is a render error that lists the supported ones). Container options belong in the service's manifest. Hand-editing `out/*` does not survive. Secrets live in a gitignored `out/secrets.env` (keys listed in the rendered `out/secrets.env.example`), not in a root `.env`. GPU/compute is decided by the render engine's hardware detection (`hardware: auto` in `ordo.yaml`, or `ordo detect`). Bring-up runs from the repo root (`ordo up --all`). Authoritative guide: [`operator-guide.md`](operator-guide.md) and `ordo.example.yaml`.

Short reference for the env vars, MCP config, and compute overrides you'll touch most often. `ordo.example.yaml` is the canonical list (plus `out/secrets.env.example` for secret keys); this page highlights the common ones and how they interact.

### Langfuse tracing (`--profile langfuse`, opt-in)

Self-hosted [Langfuse](../services/langfuse/README.md) v4: agent traces, datasets and evals.
**Opt-in**: add `langfuse` to `plugins:` in `ordo.yaml`; `plugins: auto` never enables it.
Six services (`langfuse-web`, `langfuse-worker`, `langfuse-db`, `langfuse-clickhouse`,
`langfuse-redis`, `langfuse-minio`), no host ports, reached through Caddy `:8450` /
`https://langfuse.<tailnet>.ts.net/`, plus two retention helpers (`langfuse-retention`, the daily
trace-deletion job, and `langfuse-minio-lifecycle`, a one-shot that sets the bucket expiry).

Rendered into `.env` (the last two are DEFAULTS an operator may override from `site:` in
`ordo.yaml`, unlike the other derived keys; `LANGFUSE_RETENTION_DAYS` is only in `.env` when
`site:` sets it):

| Variable | Default | Purpose |
|---|---|---|
| `LANGFUSE_ENABLED` | `1` when the plugin is enabled | Consumer-visible enable flag, like every other plugin |
| `LANGFUSE_PUBLIC_URL` | derived from the edge | Langfuse's `NEXTAUTH_URL`: `https://langfuse.<CADDY_TAILNET_DOMAIN>` with the tailnet-names sidecars, `https://<CADDY_TAILNET_HOSTNAME>:8450` with the edge alone, empty without an edge hostname. Must match the URL the browser uses or the post-login redirect strands |
| `LANGFUSE_ADMIN_EMAIL` | `admin@ordo.local` | Login identity seeded by the headless init |
| `LANGFUSE_RETENTION_DAYS` | `90` (compose default on the two retention services) | Trace retention: `langfuse-retention` deletes traces older than this through the public API (daily at 04:45 UTC) and `langfuse-minio-lifecycle` expires the `langfuse` bucket's objects after the same number of days. A positive whole number; set it with `site:` in `ordo.yaml`. The default is a compose default scoped to its two consumers (`services/langfuse/plugin.yaml`), so changing it recreates only those two |

Set on the `model-gateway` service by the renderer only while the plugin is enabled
(`ordo/render/compose.py::GATEWAY_LANGFUSE_ENV`; not `.env` keys, never hand-set):

| Variable | Value | Purpose |
|---|---|---|
| `LITELLM_EXTRA_CALLBACKS` | `langfuse_otel` | Appended to LiteLLM's `callbacks` at container start (`services/model-gateway/add_callbacks.py`); skipped with a warning if the key pair is missing |
| `LANGFUSE_OTEL_HOST` | `http://langfuse-web:3000` | OTLP export target (`/api/public/otel`), direct over `ordo-net` |
| `LANGFUSE_TRACING_ENVIRONMENT` | `gateway` | Langfuse environment of every gateway trace (Hermes's own traces use `hermes`) |
| `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` | `no_content` | Drops LiteLLM's duplicate `raw_gen_ai_request` child span; the generation keeps its input and output |

Secrets in `out/secrets.env` (all ten generated by `ordo init`; never committed):

| Variable | Purpose |
|---|---|
| `LANGFUSE_DB_PASSWORD` | `langfuse-db` Postgres password (a file for `langfuse-db`; compose-interpolated into `DATABASE_URL` for langfuse-web/worker, which have no file option) |

| `LANGFUSE_REDIS_AUTH` | Redis `requirepass` for the BullMQ ingestion queue |

| Variable | Value | Purpose |
|---|---|---|

### Voice STT/TTS (`--profile voice`)

Opt-in local speech services with OpenAI-compatible APIs. Both services run on
the **secondary GPU** by default (the smallest GPU, e.g. GTX 1070) to leave the
primary GPU free for the LLM. On single-GPU hosts they share the primary.
GPU pinning is decided by the render engine's hardware detection and baked
directly into `out/docker-compose.yml`; ops-controller's `/registry/models` reports the
resulting `voice-stt` / `voice-tts` pins, read from that render.

**Enable** (from the repo root):

```bash
ordo up stt tts
```

| Variable | Default | Purpose |
|---|---|---|
| `WHISPER__MODEL` (in `services/voice/plugin.yaml`) | `Systran/faster-whisper-base.en` | Hugging Face repo ID for faster-whisper (English base: as accurate as `small` on the stack's vocabulary, about twice as fast) |
| `STT_COMPUTE_TYPE` | `int8` | Quantization type (`int8` is Pascal-compatible; use `float16` on Turing+) |
| Hermes `tts.openai.voice` | `af_heart` | One of Kokoro's bundled voices (`GET http://tts:8880/v1/audio/voices` lists them) |

**Internal endpoints (backend network only — no host ports):**

| Service | URL | API |
|---|---|---|
| STT | `http://stt:8000/v1` | OpenAI-compatible `/v1/audio/transcriptions` |
| TTS | `http://tts:8880/v1` | OpenAI-compatible `/v1/audio/speech` (Kokoro-82M, including raw `pcm` for streaming) |

**Hermes wiring (Discord voice memos):**

- **STT (voice memo → text): fully local.** Hermes' STT openai provider takes its
  base URL from the `STT_OPENAI_BASE_URL` env, which the rendered `out/docker-compose.yml` sets on
  `agent` to `http://stt:8000/v1`. Set in the brain volume's `config.yaml` with `docker exec --user hermes ordo-agent-1 hermes config set <key> <value>`:
  `stt.provider: openai`, `stt.openai.model: Systran/faster-whisper-base.en`,
  `stt.openai.api_key: local`, `stt.enabled: true`. Inbound Discord voice messages
  are then auto-transcribed on the secondary GPU.
- **TTS (voice reply): fully local.** Set `tts.provider: openai`,
  `tts.openai.base_url: http://tts:8880/v1`, `tts.openai.model: kokoro` and
  `tts.openai.voice: af_heart`. Hermes streams speech one sentence at a time as raw `pcm`; on a
  GTX 1070 a sentence's first audio arrives 0.15-0.3 s after it is written, using about 0.8 GB of
  VRAM.
- **Desktop clients relay through the gateway.** `voice.client_direct: false` on every profile, so
  Hermes Desktop sends audio to the gateway (`/api/audio/*`), which calls these internal services. A
  desktop never needs to reach `stt`/`tts` itself.

**STT** weights download once to `${DATA_PATH}/voice/hf-cache` (persists across
recreates). **TTS** (Kokoro) ships its weights in the image; nothing is downloaded.

## Custom llama.cpp Build (inference-engine-gpu service)

The `inference-engine-gpu` service does **not** run a TurboQuant fork. `services/llamacpp-patched/Dockerfile` clones mainline [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp), pinned to the stable release v0.5.0 (commit `7fe450e19305b828c199d602c23a8337aaa1f03b`, build `b11146`), and applies exactly two patches on top:

1. **Checkpoint search fix for hybrid/recurrent models** (`tools/server/server-context.cpp`) — addresses upstream issues #22384, #20225, #24055.
2. **`recurrent_shrink`/`expand` API for prompt-cache operations** — a minimal diff for upstream PR #24785.

Both exist to support SWA/hybrid-cache models; the build fails loudly if either patch fails to apply, so bump the pinned commit only after re-verifying both still apply cleanly. The resulting image is the first-party `ordo/llamacpp-patched`: `ordo build inference-engine-gpu` builds it and records its tag, and render pins `out/docker-compose.yml` to that tag.

The build compiles CUDA kernels for sm_120 (Blackwell) only, so every catalog model that pins it declares `requires.min_compute_cap: "12.0"`, and the sizer only picks those models on a GPU known to meet it (see Compute Configuration below). Models without a `backend_image` run the host's upstream build.

### KV-cache quantization

The `LLAMACPP_ENABLE_KV_CACHE_QUANTIZATION` / `LLAMACPP_KV_CACHE_TYPE_K` / `LLAMACPP_KV_CACHE_TYPE_V` vars (set in `ordo.yaml`, re-render to apply) are real and wired into `scripts/llamacpp/run-llama-server.sh` as `--cache-type-k` / `--cache-type-v`. Both default to `q4_0` when quantization is enabled. Because this is a mainline build, only mainline's KV-cache types are valid (`q8_0`, `q4_0`, `q4_1`, `q5_0`, `q5_1`, `iq4_nl`, `f16`); TurboQuant `tbq*` types do not exist on this build and the server rejects them at startup.

### Rollback to stock upstream

In `ordo.yaml`, point the chat service at the pinned upstream CUDA build (the `CUDA` image in `ordo/render/llamacpp_backend.py`):
```yaml
overrides:
  inference-engine-gpu:
    image: ghcr.io/ggml-org/llama.cpp:server-cuda12-b11552@sha256:9d835c2febd6f09a0aafb30e9c1b29a67a49923b67075993551ab4593d84491f
```
Re-render, then from the repo root: `ordo recreate inference-engine-gpu` (refused while a GPU lease has it evicted). This drops the two hybrid/recurrent patches above, so a `qwen35`-arch model may no longer load on it.

### CPU fallback thread budget

`inference-engine-cpu` serves `local-chat` while a render holds the GPU, so its CPU load lands on top of the render's peak power draw. Unbounded, llama.cpp took about 24 of 48 threads, enough to trip the host UPS's overload alarm. Its budget is one source value:

```yaml
overrides:
  inference-engine-cpu:
    threads: 12
```

- Default when unset: `min(12, half the detected logical CPUs)` (`ordo detect` shows the core count).
- Renders to `--threads N`, `--threads-batch N` and the service's compose `cpus: N` limit, so the argv and the ceiling agree.
- Must be a whole number from 1 to the detected logical CPUs; anything else is a render error.
- The GPU chat service (`inference-engine-gpu`) is not affected.
- `ordo doctor` prints the declared value next to what the running container has, and flags a mismatch (for example a hand `docker update --cpus`, which leaves no trace in the config hash). Apply a change with `ordo apply --only inference-engine-cpu`.

### CPU fallback context window

There is one chat window. The GPU backend (`LLAMACPP_CTX_SIZE`), the CPU fallback (`LLAMACPP_CPU_CTX`), Hermes (its `context_length`, and so its compaction trigger) and model-gateway (`max_input_tokens` of `local-chat` and of the CPU deployment) all read the same resolved value. The fallback serves `local-chat` while a render holds the GPU, so a smaller fallback window would reject long conversations exactly then; with one window, a conversation Hermes has not compacted fits wherever it is routed.

The render proves the fallback can serve that window instead of assuming it:

- The fallback's catalog entry (`support_models`, `qwen3.8-35b-a3b-distill-cpu-iq4xs`) declares its trained window (`ctx_default: 262144`, from the GGUF header) and its KV rate (`kv_kb_per_token: 10.625`: 10 full-attention layers x 2 KV heads x 256, q8_0).
- A chat window larger than the fallback's trained window is a render error that names both windows and the fix (`overrides.inference-engine-gpu.ctx_size` at or below the fallback's window, or disable `inference-engine-cpu`). It is never served by a silently smaller fallback.
- Weights named by a `site: LLAMACPP_CPU_MODEL` that the catalog does not list render with a warning: their window is unchecked.
- `out/manifest.json` (`cpu_fallback`) and `ordo doctor` (`windows :` line) show both windows and what the window costs the fallback in RAM.

What a window costs the fallback (q8_0 KV, ~63 MiB of recurrent state on top, constant):

| Window | KV | Weights | Measured resident |
|---|---|---|---|
| 106,496 | 1.08 GiB | 18.28 GiB | 20.1 GiB |
| 262,144 | 2.66 GiB | 18.28 GiB | 21.2 GiB |

On the reference host (Docker VM 102 GiB, ~61 GiB available with the fallback already resident at 106,496) the 262,144 window costs about 1.1 GiB more, so the fallback runs at the full window.

The window is an allocation, not per-request work: llama.cpp prefills only the tokens sent. A cold failover still has to prefill the whole conversation on CPU, measured at about 25 tokens/s on long conversations (measured with the previous Qwen3.6 UD-Q4_K_M weights at 512-token batches), so a conversation much past ~45k tokens does not finish its first fallback turn inside the gateway's 1800 s timeout. That timeout is a visible error, not a truncation; it is a property of CPU prefill, not of the window.

## Served Models

ops-controller derives what the stack serves from the current render (`ordo.yaml`, the model
catalog and the rendered compose) on every call; nothing is stored. Each record names the model
id, service, the file it loads, its GPU pin and, for `local-chat`, the context window and vision
projector:

| Endpoint (ops-controller) | Method | Purpose |
|---|---|---|
| `/registry/models` | GET | Every model the render serves (`local-chat`, `local-chat-cpu`, `local-embed`, `comfyui`, `voice-stt`, `voice-tts`, for the services that are rendered) |
| `/registry/gpus` | GET | Live GPU inventory with the models the render pins to each GPU |
| `/model-config` | GET | The active model, its file and projector (`active_file`, `active_mmproj`), and `model_files`: every file a rendered service loads |

The dashboard proxies the first two as `/api/orchestration/registry/*`, and the `orchestration` MCP server exposes them as `list_models` and `gpu_status`. The dashboard's model-file delete refuses every file in `model_files` and every file a server has loaded. GPU pins are baked in at `ordo render` time, so `POST /gpu/assign` and `POST /registry/models/{id}/assign-gpu` answer 410.

The active chat model is the `model:` key in `ordo.yaml`, and its projector is the catalog entry's `mmproj`: switch it from the dashboard's Models page or the `set_active_model` MCP tool. Both call the dashboard's `POST /api/models/switch`, which calls `ops-controller` `POST /model-config`: it writes `ordo.yaml`, re-renders, and recreates exactly the services the render changed (`inference-engine-gpu` and `model-gateway`; `inference-engine-cpu` too when the context window changed). The agent reads the window as well but is never cycled from the control plane: the response names it in `restart_required_on_host` with the host command (`ordo apply --only agent`). A switch is refused while a GPU render lease is held, and a failed apply rolls `ordo.yaml` back.

### Gateway aliases

The served-model ids above are what the stack runs. The model gateway additionally exposes stable
aliases over the two chat deployments, which is how clients choose a routing policy (the
deployment-derived pins change name on every model swap and are not grantable to keys). Only
`local-chat` and `local-chat-cpu` are served-model ids; `local-chat-gpu` is a gateway alias of the
same GPU deployment and does not appear in `/registry/models`:

| Alias | Serves | When to use |
|---|---|---|
| `local-chat` | the GPU chat model, failing over to the CPU fallback while a render holds the GPU | the default for every consumer: a turn is never lost to a GPU failure |
| `local-chat-gpu` | the GPU chat model only, with no CPU failover | work that must run on the GPU and accepts an error while the model is evicted for a render |
| `local-chat-cpu` | the CPU fallback (unloads its model after 10 idle minutes; the next request reloads it in ~20 s) | work deliberately routed off the GPU (batch jobs, overnight crons); it holds no VRAM, so it runs in parallel with GPU work |

## Local Model Cost

`ordo.yaml`'s optional `cost:` block derives a real per-token price for every local model
(`local-chat`, the GPU pin, the CPU pin, `local-embed`) from the operator's electricity rate and
measured throughput, so the LiteLLM UI's spend-per-key and the `x-litellm-response-cost`
response header mean something instead of always reading $0.

| `ordo.yaml` key (under `cost:`) | Required | Purpose |
|---|---|---|
| `usd_per_kwh` | yes, if `cost:` is set | Operator's electricity rate in $/kWh |
| `inference_watts` | yes, if `cost:` is set | Rig power draw while inferencing (GPU power cap plus host) |
| `prompt_tokens_per_second` | yes, if `cost:` is set | Measured prompt-processing throughput |
| `output_tokens_per_second` | yes, if `cost:` is set | Measured generation throughput |

Leaving `cost:` unset (or `{}`) keeps every local model at $0/token, same as before this existed.
When set, all four keys are required and must be positive numbers; a missing, zero, negative, or
unrecognized key fails the render with a `ValueError` naming it (see
`ordo/render/engine.py::local_token_costs`). The render engine computes:

```
usd_per_second = inference_watts / 1000 * usd_per_kwh / 3600
input_cost_per_token  = usd_per_second / prompt_tokens_per_second
output_cost_per_token = usd_per_second / output_tokens_per_second
```

and emits the results into `.env` as `LOCAL_INPUT_COST_PER_TOKEN` / `LOCAL_OUTPUT_COST_PER_TOKEN`
(see the table above), which the model-gateway entrypoint substitutes into
`__LOCAL_INPUT_COST_PER_TOKEN__` / `__LOCAL_OUTPUT_COST_PER_TOKEN__` placeholders in
`litellm_config.yaml` (see [services/model-gateway/README.md](../services/model-gateway/README.md)).

## MCP Server Configuration

An MCP server is declared as a `kind: mcp` plugin manifest at `services/<id>/plugin.yaml`, with an
`mcp:` block: `transport: http`, `image` or `url`, `port`, `path`, `network: internal|stack`, `env`,
`secrets`, `volumes`, `timeout`, `auth`, `allowed_tools`, `tools`. See
[services/model-gateway/README.md](../services/model-gateway/README.md).

Enabled servers render as compose services `mcp-<server_id>` on the internal `ordo-mcp-net`
network: only `model-gateway` can reach them.

`ordo render` emits `out/model-gateway/mcp_servers.yaml` (merged into LiteLLM's config by the
entrypoint) and `out/mcp/servers.json` (the enabled-server list plus the registered-plugin
map).

The registered servers are `comfyui`, `orchestration`, `qdrant-rag`, `searxng`,
`codebase-memory`, and `memory-vault`: there are no `duckduckgo` or `playwright` defaults.

Enable or disable a server by editing `ordo.yaml`'s `plugins:` list (or through ops-controller's
`POST /plugins/{id}/...`, which edits the same file). A toggle there is applied by ops-controller:
LiteLLM reads config-file MCP servers at startup, and model-gateway's definition carries a digest of that config,
so the render's changed set recreates it. After a hand edit, `ordo apply` does the same.

## Compute Configuration

Hardware detection and GPU pinning are done by the render engine, not a standalone script. `hardware: auto` in `ordo.yaml` (or `ordo detect`) probes the machine at render time, and `ordo render --out out` (run from the repo root) bakes the result directly into `out/.env` and `out/docker-compose.yml`. Re-run `ordo render` to re-detect after a hardware change.

To override manually, pin an explicit `hardware:` block in `ordo.yaml` instead of `auto` (see the commented example in `ordo.example.yaml`), then re-render:

```yaml
hardware:
  gpus: [{ name: "RTX 5090", vram_gb: 32, vendor: nvidia, compute_cap: "12.0" }]
  ram_gb: 128
  cpu_cores: 32
  platform: Linux
  arch: x86_64
```

`vendor` is `nvidia` (the default), `amd`, `intel` or `apple`. `compute_cap` is NVIDIA only (`nvidia-smi --query-gpu=compute_cap --format=csv`); without it, models that need a specific build (the patched sm_120 image) are skipped with a warning. `arch` is `x86_64` or `arm64` and defaults to this machine's.

**llama.cpp backend.** `ordo/render/llamacpp_backend.py` maps the primary GPU to one upstream llama.cpp server image, all pinned to one build by tag and digest:

| Primary GPU | Backend | Device wiring |
|---|---|---|
| none, Apple (Docker has no Metal) | `cpu` | none |
| NVIDIA, compute capability 5.0+ or unknown | `cuda` | `driver: nvidia` reservation, pinned by uuid |
| AMD on x86_64 | `rocm` (experimental) | `/dev/kfd`, `/dev/dri` |
| AMD on arm64, Intel | `vulkan` (experimental) | `/dev/dri` |

A catalog model's `backend_image` replaces the image, never the device wiring. NVIDIA-only plugins (`requires.nvidia`) and every `driver: nvidia` reservation are rendered only when the primary GPU is NVIDIA. The ROCm and Vulkan paths are rendered and `docker compose config`-validated but have not run on real AMD or Intel hardware.

**ComfyUI `CLI_ARGS`:** Set `COMFYUI_CLI_ARGS` under `site:` in `ordo.yaml` (it flows verbatim into the rendered `.env`) and re-render. Without it, the rendered default is `--cpu --enable-manager`.

**ComfyUI custom-node deps:** The `comfyui` container's startup wrapper auto-installs every `requirements.txt` it finds under `/root/ComfyUI/custom_nodes/*/` before launching ComfyUI. Idempotent (pip skips already-satisfied specifiers). Adding a new custom node? Drop it under `data/comfyui-storage/ComfyUI/custom_nodes/` and, from the repo root, `ordo recreate comfyui` — its deps land automatically. Failures on individual files (e.g. malformed pin) are logged as `[deps] WARN failed` and don't block startup. Packs the stack depends on are additionally pinned by commit in `scripts/comfyui/custom_nodes.json`; a drifted pack is moved back to its pinned commit on boot ([ComfyUI application version](#comfyui-application-version)). A dropped-in pack keeps its local changes until you list it there; a pack without `.git` is replaced wholesale on the next boot after listing, so move any downloaded weights out of its directory before listing it.

## Data Persistence Rules

volumes** (ext4 inside the Docker VM — Windows bind mounts ride the 9p bridge, which
wedges under heavy or metadata-dense I/O), while **operator-facing drop zones and
small config** stay host bind-mounted so they are reachable from Windows.

### ComfyUI application version

The pinned `COMFYUI_IMAGE` digest pins the *runtime* (torch, CUDA, the boot entrypoint). The
ComfyUI application itself lives on the `comfyui-app` volume, so the image says nothing about
which ComfyUI is running. That version is declared separately, as **`COMFYUI_APP_REF` in
`services/comfyui/plugin.yaml`** — a full upstream commit SHA, never a tag or branch.

`scripts/comfyui/boot.sh` runs as the container command and reconciles the checkout to that ref
on every start. If the volume has drifted it fetches and checks out the declared ref; if it
cannot, it refuses to start rather than serve a version nobody declared. The Comfy-Org runtime
pins (`comfyui-frontend-package`, `comfy-kitchen`, `comfy-aimdo`, …) are read out of that ref's
own `requirements.txt`, so the app and its runtime deps cannot drift apart.

The same treatment extends to the **custom node packs** the stack's graphs import: each is
declared with a full commit SHA in `scripts/comfyui/custom_nodes.json` (bind-mounted read-only at
`/comfyui-scripts/custom_nodes.json`) and reconciled by the same boot script — a missing pack is
cloned, a drifted one is fetched and detached to its pinned commit, and a pack that cannot reach
its ref stops the boot, like an undeclared app. Listing a pack is what makes it reproducible:
when a listed pack has drifted from its pinned commit, boot moves it back to that commit and
discards local edits to tracked files (in a pack that is already a git checkout, untracked files
such as downloaded weights are left in place), so bump the ref deliberately instead of patching
the pack. A pack with no `.git` (a zip copy or hand install) is replaced wholesale, so move any
weights out of its directory before listing it. Packs on the volume the file does not list are
left untouched.

To move ComfyUI versions:

```bash
# 1. edit COMFYUI_APP_REF in services/comfyui/plugin.yaml to the new commit SHA
ordo render
ordo up --all
# 2. confirm declared == running
docker compose -p ordo exec comfyui git -C /root/ComfyUI rev-parse HEAD
```

Rolling back is the same edit in reverse — the reconciler downgrades the checkout and re-pins the
runtime deps to the older ref's `requirements.txt`.

Current pin: **v0.41.1** (`45bf90d1`), the first release carrying FLUX 3 Image support. The previous
pin, **v0.37.0** (`73c9bad4`), is the immediate rollback — it cannot detect the flux3 transformer,
so a rollback there is only valid together with switching the timelapse image pipeline from the
default flux3 templates to the Qwen-Image 2.1 ones (set `TIMELAPSE_T2I_TEMPLATE=qwen21_t2i.json`
and `TIMELAPSE_EDIT_TEMPLATE=qwen21_edit.json`; the overrides are read on the Hermes side by the
ai-timelapse-short skill). **v0.33.1** (`72865f4f`) remains the floor: it is the first release
carrying the MiniMax Music3 nodes that `services/song-gen` declares, so never roll back below it.

## Network Ports

Caddy is still the **only** service with published host ports, every other service (dashboard, open-webui, model-gateway, litellm-db, comfyui, langfuse-web, the `mcp-*` servers, qdrant, ops-controller, etc.) has no `ports:` entry and is reachable only from other containers on the internal `ordo-net` network. But since 2026-07-24 Caddy itself is **port-per-service**: it publishes the SSO-gated host ports below on `${CADDY_TAILNET_HOSTNAME}` (all bound to `CADDY_BIND`) instead of routing every UI under subpaths of a single `:443`. Each prebuilt SPA is served at the root it was compiled for, ending the subpath-rewrite workarounds (Open WebUI root-catchall 404s, Hermes header-based base injection, codebase-memory nginx rewrites).

One Google sign-in covers every port except Hermes's `:8447` (its own sign-in) **and the clean per-service tailnet names** — the oauth2-proxy session cookie is domain-scoped, the one OAuth callback stays on `:443`, and the SSO gate's `rd=` redirect carries `{host}` (portless), so a single wildcard `--whitelist-domain=.<domain>` in the edge plugin covers every port and every sidecar name. A first sign-in through a bare `:844x` port lands on the `:443` hub and the domain-scoped cookie then covers everything (one extra click); the clean tailnet names (`chat`/`dash`/… `.<tailnet>.ts.net`) return you straight to the service. No new Google OAuth redirect URIs are needed. See [deployment-models.md](deployment-models.md) for the clean-URL sidecar layer.

| Port | Service | Notes |
|---|---|---|
| `443` | Front door | Landing page; `/oauth2/*` (the one Google callback); `/llm/*` → LiteLLM API (Bearer, SSO-bypassed); `/mcp` → model-gateway's MCP endpoint (Bearer LiteLLM key, SSO-bypassed); 302s from every legacy subpath (`/chat`, `/dash`, `/comfy`, `/hermes`, `/codebase-memory`, `/grafana`) to its new port |
| `8443` | Open WebUI (chat) | Served at root |
| `8444` | Dashboard | Served at root; Grafana rides along at `/grafana/` on this port |
| `8446` | ComfyUI | Served at root |
| `8447` | Hermes | Served at root; Hermes's own Google OIDC sign-in, not oauth2-proxy ([runbooks/auth.md](runbooks/auth.md)) |
| `8448` | codebase-memory | Served at root (the container's nginx now proxies straight through, no `sub_filter`) |
| `8449` | LiteLLM admin UI | Served at root; the admin UI lives at `/ui/` and swagger at `/`. Distinct from the `/llm/*` API route on `:443`, which stays the SSO-bypassing programmatic base |
| `8450` | Langfuse | Served at root; the only route into `langfuse-web` (agent traces, datasets, evals). Hermes ingests directly over `ordo-net`, not through this port |
| (none) | Everything else | Reachable service-to-service by container DNS name (e.g. `http://ops-controller:9000`), never from the host or LAN directly |

Old subpath URLs (`/chat`, `/dash`, `/comfy`, `/hermes`, `/codebase-memory`, `/grafana`) still work — Caddy 302s them from `:443` to the matching port — so existing bookmarks don't break.
